## 物理

```
ω = I(q)⁻¹ ( R(t)ᵀ H0 − h_rel(q, q̇) )
```

- `I(q)` … 全身CMまわりの慣性テンソル（体幹系）。平行軸定理で毎時刻組み直す
- `h_rel` … 関節運動による相対角運動量（体幹の角速度を0としたときの全身CMまわり）
- 姿勢は quaternion を RK4 で積分。関節の角速度は姿勢の中心差分（h=1e-4）から出す
- 剛体18体（ポール込みで20体）。設計書の4体案の上位互換

## 人体セグメントパラメータ

**de Leva (1996) Table 4, male**（基準体 73.0 kg / 1.741 m）
de Leva P. *Adjustments to Zatsiorsky-Seluyanov's segment inertia parameters.*
J Biomech 29(9):1223-1230, 1996.

質量比は身長・体重（仮値 1.70 m / 65 kg）にスケールし、**身体ぶんの合計は 65.000 kg ちょうど**になる。
慣性は `I = (M·m̄)·(l·r)²`（原典の式）で、矢状/横/長軸の3軸ぶんを個別に計算している。

### なぜ Winter (2009) Table 4.1 を使わないか（自分でも確認済み）

Winter の慣性半径の3列は **C of G / Proximal / Distal** で、**同じ軸まわりの基準点違い**。
平行軸定理で一致することを確認した（大腿: √(0.323²+0.433²)=0.540 = ρ_prox、
√(0.323²+0.567²)=0.653 = ρ_dist）。つまり**長軸まわりの値が無い**ので、
ひねりを扱う本アプリでは使えない。de Leva は3軸を男女別に与えているので採用した。

## 座標・軸

体幹系：原点＝股関節中点、**+Y=体幹長軸（上）／+X=前／+Z=左**。
セグメントのローカル系も同じで、四肢は +Y が長軸。
**足だけは長軸が踵→爪先なので +X が長軸**（`longAxis:'x'`）として扱っている。

### A-2 解析式との突き合わせ

`ψ̇_analytic = |H|·sin(tilt)·(1/I_L − 1/I_T)` を、ソルバ自身の I(q) を使って比較した。

| 条件 | ψ̇ソルバ / ψ̇解析式（中央値） |
|---|---|
| 離地の傾き 10.4°（実際の動作点） | **0.934**（平均 0.983 ± 0.127、21点） |
| 離地の傾き 0°（小tilt域） | **0.679**（平均 0.693 ± 0.047、5点） |

**動作点では数%で一致する**（Euler分解の取り出し方は独立に裏付けられた）。
小tilt域では系統的に 0.68 倍にずれる。**原因は慣性乗積（非対角成分）**で、解析式はこれを無視している。

`stepA2.js` で切り分けた。完全な I で解いた ω_y と、対角成分だけにした I で解いた ω_y を比べると：

| 条件 | ω_y(完全I) / ω_y(対角のみ) |
|---|---|
| 離地の傾き 0° | **0.722** ← ψ̇ の比 0.679 とほぼ一致 |
| 離地の傾き 10.4° | **0.957** ← ψ̇ の比 0.934 とほぼ一致 |

慣性乗積は Ixy ≈ 0.53〜0.62、Iyz は最大 −0.33 で、**I_L の 15〜19%**。

#### 発生源（`ixy_check.js` で切り分け・訂正あり）

当初「片腕の外転が軸対称を崩している」と書いたが、**これは誤り**だった。

| 条件 | τ=0.30（腕 非対称） Ixy / Iyz | τ=0.70（腕 左右対称） Ixy / Iyz |
|---|---|---|
| 装備あり | **0.602** / −0.286 | **0.527** / 0.000 |
| 板+ビンを0 | **−0.069** / −0.229 | **−0.145** / 0.000 |
| ブーツを0 | 0.566 / −0.251 | 0.493 / 0.000 |
| 足元すべて0 | −0.140 / −0.188 | −0.214 / 0.000 |

- **Ixy は板＋ビンディング由来。** 板+ビンを0にすると 0.602 → −0.069 に落ちる。
  ブーツの寄与はごく小さい（0.04程度）。**腕が左右対称のときも同じ大きさで存在する。**
- **Iyz が腕の非対称由来。** 左右対称に戻ると 0.000 になる。

→ **板は「ひねり軸の慣性を増やす」だけでなく、身体を軸対称でなくしている。**
  だから軸対称を仮定した教科書のツイスト式がそのままでは当てはまらない。
  Yeadon の「ひねりを作る難しさは実は tilt を作る難しさ」に、モーグル特有の第2の理由が加わる。

小tilt域で効きが大きいのは、H の身体長軸成分が小さく、非対角経由の寄与が相対的に大きくなるから。
（残差は φ̇ も厳密には H/I_T ではないことによる）

**結論：解析式は動作点では使えるが、小tilt域では 0.7 倍程度に見積もり直す必要がある。**
ソルバ側は非対角成分を含めて解いているので、こちらを正とする。

### B-6 への回答（先に）

時系列の **−7.6°** と公開テーブルの **−5.9°** は、**どちらも正しく、別の量**。

- **−7.6°** = `∫ω_y dt`（身体長軸まわりの角速度の積分）
- **−5.9°** = 幾何的な Euler の ψ（テーブルが持っている値）

両者は `ω_y = ψ̇ + φ̇·sin(tilt)` の関係で `−sin(tilt)·dφ` だけ違う。
慣例の「ひねり」は後者なので **−5.9° を使う**。
τサンプル 51 の解像度は関係ない（dt=1/1500 の生データでも τ=1.00 で −5.9°）。

## B の結果（2026-08-19）

### B-1 モデルを凍結した

### B-2 Cork で何をフィットし、何を予測するか（先に固定）

| 区分 | 対象 |
|---|---|
| **フィットしてよい** | `|H0|` の**大きさのみ**。ただし **Cork 自身の宙返り進行から決める。Back Full の値（84〜89）を流用しない** |
| **測定から与える** | `q(t)`（関節角）、初期姿勢、読めれば `H0` の**向き** |
| **絶対にフィットしない** | **`tilt(t)` と `twist(t)`** |

映像から推定した H は**正解として扱わない**。微分を伴うのでノイズに弱く、
Yeadon の11セグメント法でも相対誤差は約10%と見積もられている。
保存性と向きの安定性を見る用途に留める。

### B-3 呼び方

このモデルは「完全な予測モデル」ではなく **「1パラメータ校正済みモデル」**。

- **校正するもの**：`|H0|` の大きさ1個だけ。**総宙返り360°** に合わせている
- **予測として検証するもの**：**90 / 180 / 270° の到達時刻**、`tilt(t)`、`twist(t)`

### B-4 感度範囲 — ひねり360°に必要な離地の傾き

`stepB4.js` / 出力 `stepB4_result.txt`。`|H0|` は条件ごとに離地の傾き10°で1回合わせ、条件内は固定。
宙返り総量は全条件で 357〜365°（±2%）に収まっており、同じ技どうしの比較になっている。

| 条件 | 必要な離地の傾き |
|---|---|
| 現行の左右割当／ポール無／ビン0.875（基準） | **10.40°** |
| **★左右入れ替え**／同上 | **8.96°**（**−1.44° / −13.9%**） |
| ポール 0.20 kg | 10.80° |
| ポール 0.25 kg | 10.88° |
| ポール 0.30 kg | 10.95° |
| ビンディング 0.50 kg | 10.11° |
| ビンディング 1.25 kg | 10.69° |

**左右の割り当てが最大の感度**（−13.9%）。ポールは +0.4〜0.55°、ビンディングは ±0.3° と小さい。

理由：現行の割り当てだと腕の非対称が作る tilt は **負**（−2.5°）で、離地時に与えた正の傾きを
打ち消す向きに働く。入れ替えると同じ向きに足されるので、必要な離地の傾きが減る。

→ **headline は単一値ではなく `約9〜11°`。** さらに剛体近似の 8.3° を含めると **`約8〜11°`**。
   `sideAssignment` が確定するまで、この幅は縮まらない。

### §5 生成物の管理

`table.js` の先頭に **生成日時・モデル名・使った表・本体の sha256** を入れた。
`gen_table.js` は、既存 `table.js` と内容が変わる場合 **上書きせず exit 2 で止まる**
（更新してよいときだけ `bun gen_table.js --write`）。

このガードは**最初の実行でさっそく効いた**。当時 `gen_table.js` の出力と公開中の
`table.js` は `somTotal` / `twistTotal` の規約がずれていた（公開版は `fixup.js` で
後処理して「増分」にしていた）。ガードが差分を検出したので、規約を `gen_table.js` 本体に
取り込み、**いま `gen_table.js` だけで公開中の table.js を byte 一致で再生成できる**
ことを確認した（本体 sha256 `1d93e426d6459d8f`）。`fixup.js` は無効化した。
